gita 仕様

1. 概要

gita は登録した複数の git リポジトリ（以下 repo）に対して、次の 2 つを行う Rust 製の CLI である。

  • gita ll で各 repo のブランチ、変更状態、最新コミットを横並びに表示する。
  • どのディレクトリからでも、選んだ repo 群に git コマンドやシェルコマンドを一括で実行する。複数 repo のときは並列に実行する。

動作環境

項目要件
OSWindows、macOS、Linux
git2.35 以上（status --show-stash を使うため）。PATH 上にあること。ll は gix で読める repo では git を起動しない。
バイナリ名gita

コマンドの分類

分類コマンド説明
管理系add scan rm rename ls ll group context flags color info clear設定ファイルを読み書きし、情報を表示する。
委譲系設定に定義されたもの（fetch pull st など 22 個 + ユーザー定義）定義済みの git コマンドを repo ごとに実行する。
任意実行super shell任意の git コマンド、任意のシェルコマンドを実行する。
移行freeze clonerepo 一覧を書き出し、別の環境で clone し直す。

2. 設定ファイル

2.1 設定ディレクトリ

次の順で最初に当てはまるものを設定ディレクトリとする。環境変数は空文字なら未設定とみなす。

順条件設定ディレクトリ
1GITA_PROJECT_HOME が設定済み$GITA_PROJECT_HOME/gita
2XDG_CONFIG_HOME が設定済み（全 OS）$XDG_CONFIG_HOME/gita
3Windows%APPDATA%\gita（例 C:\Users\u\AppData\Roaming\gita）
4Linux / macOS~/.config/gita

Windows では dirs::config_dir()（Known Folder API の FOLDERID_RoamingAppData）で %APPDATA% を得る。理由は次のとおり。

  • Windows アプリの設定の標準の置き場所であり、ユーザーがエクスプローラーや %APPDATA% で見つけやすい。
  • Roaming のため、ドメイン環境ではプロファイルと一緒に移動する。repo の一覧は利用者に付く設定なので Roaming が合う（キャッシュのようなマシン固有のデータではない）。
  • ~/.config は Windows では慣習がなく、ホーム直下に隠しでもないフォルダが増える。

macOS は dirs::config_dir() だと ~/Library/Application Support になるが、CLI ツールの慣習に合わせて ~/.config を使う。

2.2 ファイル一覧

コマンドが書き換える状態と、利用者が手で編集する設定を別ファイルに分ける。どちらも UTF-8、2 スペース字下げ、末尾改行ありで書く。

ファイル書く主体内容無いとき
repos.jsongita のコマンド登録 repo、グループ、コンテキストすべて空
settings.json利用者（color set info add なども書く）表示設定、ユーザー定義コマンド、並列数すべて既定値

2.3 repos.json

{
  "version": 1,
  "repos": {
    "gita": { "path": "/home/u/src/gita", "type": "", "flags": [] },
    "dotfiles": {
      "path": "/home/u/dotfiles.git",
      "type": "",
      "flags": ["--git-dir=/home/u/dotfiles.git", "--work-tree=/home/u"]
    }
  },
  "groups": {
    "src": { "path": "/home/u/src", "repos": ["gita", "dotfiles"] },
    "work": { "path": null, "repos": ["api", "web"] }
  },
  "context": null
}
キー型説明
versionnumber形式のバージョン。今は 1。より大きい値なら「新しい gita で作られた」旨を出して終了コード 1。
reposobject（キー = repo 名）登録順を保つ（serde_json の preserve_order）。キーなので名前は重複しない。
repos.*.pathstring絶対パス。
repos.*.typestring予約欄。現在は freeze がそのまま出力するだけ。省略可。
repos.*.flagsstring[]git のグローバルオプション。git の直後に挿入する。配列なので空白を含む値も 1 要素として扱える。省略可。
groupsobject（キー = グループ名）repos はメンバー名の配列。path は string か null。
contextstring か nullnull = なし、"auto" = 自動、それ以外 = グループ名。
  • 読み込み時、存在しない repo を指すグループのメンバーは無視する（ファイルからは消さない）。
  • パスが存在しない repo（外付けディスクの取り外し中など）も設定からは消さない。表示や実行の対象から外すだけにし、ll では (missing) と表示する。
  • メンバーが 0 件になったグループは書き込み時に削除する。

2.4 settings.json

{
  "jobs": null,
  "backend": "auto",
  "colors":  { "no_remote": "white", "in_sync": "green", "diverged": "red",
               "local_ahead": "purple", "remote_ahead": "yellow" },
  "info_items": ["branch", "commit_msg", "commit_time"],
  "layout":  { "branch": 19, "symbols": 5, "branch_name": 27,
               "commit_msg": 0, "commit_time": 0, "path": 30 },
  "symbols": { "dirty": "*", "staged": "+", "untracked": "?", "stashed": "$",
               "local_ahead": "↑", "remote_ahead": "↓", "diverged": "⇕",
               "in_sync": "", "no_remote": "∅" },
  "commands": {
    "fetchcrt": {
      "cmd": "git rev-parse --abbrev-ref HEAD | xargs git fetch --prune upstream",
      "allow_all": true,
      "shell": true,
      "help": "fetch current branch only"
    }
  }
}
  • すべてのキーは省略でき、省略したキーは既定値になる。colors symbols layout は一部のキーだけ書けば、残りは既定値とマージする。
  • layout を省略したときは切り詰めない。上の値は info set-length が書き込む値。
  • jobs は並列数の上書き（10.4）。backend は状態の読み取り方法（11.5）。
  • gita がこのファイルを書き換えるとき、知らないキーも残す（#[serde(flatten)] で保持する）。
  • 不正な JSON のときは、ファイル名と行・列を出して終了コード 1。黙って既定値に戻さない。

2.5 commands（委譲コマンドの定義）

キー型既定意味
cmdstring か string[]必須実行するコマンド。文字列なら空白で分割して argv にする（shell が真なら分割しない）。配列ならそのまま argv にする（空白を含む引数を書ける）。
helpstringなしヘルプ文。
allow_allboolfalse真なら repo 指定を省略でき、省略時は全 repo（またはコンテキスト）が対象。
disable_asyncboolfalse真なら複数 repo でも逐次実行し、端末入出力を直接つなぐ。
shellboolfalse真なら cmd をシェル経由で実行する。

既定の 22 個（7.1）はバイナリに埋め込む。settings.json の commands は同名の既定定義を上書きする。組み込みコマンド（add など）と同名の定義は無視し、警告を出す。

2.6 git repo の判定

  1. パスが存在しなければ偽。
  2. <path>/.git が有効な Git ディレクトリなら真。.git がファイルの場合は、ファイルが指す Git ディレクトリを検証する。
    exclude_submodule 指定時、.git がファイルで中身に .git/modules を含むなら偽。
  3. include_bare 指定時のみ、git rev-parse --is-bare-repository を path で実行し、終了コード 0 かつ出力が true なら真。
  4. それ以外は偽。

3. CLI 全体の規則

  • トップレベルのオプションは -h/--help、-v/--version（gita <version> を出力）、-j/--jobs N。
  • サブコマンドなしで起動したらヘルプを表示する。
  • repo 名、グループ名を取る引数は、実行時に設定から選択肢を作る。選択肢外なら使い方を表示して終了コード 2。
  • 委譲系サブコマンドは設定から実行時に生成する。clap では builder API で動的に追加する。
  • グループ名には repo 名、既存グループ名（group add では許可）、予約語 none auto を使えない。違反時はメッセージを出して終了コード 1。
  • パス引数は std::path::absolute で絶対パスにする。シンボリックリンクは解決しない。

4. 対象 repo の解決

4.1 コンテキスト

repos.json の context で、既定の対象グループを決める。

  • null ならコンテキストなし。
  • グループ名ならそのグループ。グループが消えていればコンテキストなしとして扱う。
  • "auto" なら、各グループの path のうちカレントディレクトリを含むものを探し、カレントディレクトリからの相対深さが最小のグループを選ぶ（同点なら先に定義されたもの）。path が null のグループは候補にしない。該当なしならコンテキストなし。

Windows ではパスの比較で大文字小文字を区別しない。

4.2 引数からの解決

super、shell、委譲系で共通に使う。

  1. 引数に -- があれば 4.3 の明示モードで解決する。
  2. 引数を先頭から見て、repo 名またはグループ名である限り名前として取る。最初に名前でない語が出たところで止め、そこから後ろを「残り」とする。
  3. 名前が 0 個で、コンテキストがあれば、コンテキストのグループを名前とする。
  4. 名前があれば、repo 名はその repo、グループ名はメンバー全員に展開する（重複は 1 回、順序は出現順）。名前がなければ全 repo。
  5. quote_mode（-q）のときは、残りがちょうど 1 語でなければ <語> is not a repo or group を出して終了コード 2。

4.3 repo 名とコマンドの曖昧さの解消

repo 名とコマンドが同じ語だと、4.2 の規則では区別できない。例えば repo status があると、gita super status は「repo status を対象にコマンドなし」と解釈される。これに次の 3 つで対処する。

対策内容
-- による明示gita super status -- status、gita super -- status（コンテキストまたは全 repo が対象）。-- より前はすべて repo 名かグループ名でなければならず、違えば <語> is not a repo or group で終了コード 2。-- より後はすべてコマンドとして扱う。shell でも同じ。
登録時の警告add、rename、group add -n、group rename で、名前が git のコマンドまたは alias（git --list-cmds=main,others,alias の結果）と一致したら、-- を使うよう案内する警告を stderr に出す。登録は行う。
取り違えの検出-- なしで残りが空になったとき、最後に名前として取った語が git コマンドとしても有効なら、Missing commands に加えて「<語> を repo 名として扱った。コマンドとして使うなら -- を付ける」と案内する。

委譲コマンド（gita st ...）は引数がすべて名前なので、この曖昧さは起きない。

5. 管理系コマンド

5.1 add

gita add <path>... [-n] [-g GROUP] [--group-path PATH] [-s] [-r | -a | -b]
オプション動作
-n, --dry-run見つかった件数とパスを表示し、書き込まない。
-g, --group追加した repo をグループに入れる。グループがなければ <g> does not exists, creating it. を出して作る。
--group-path新規作成するグループの path。
-s, --skip-submodulesubmodule を除外する。
-r, --recursive各パス以下の全ディレクトリ（自身を含む）を候補にする。
-a, --auto-group-r と同じく再帰で探し、ディレクトリ構造からグループを自動生成する。
-b, --barebare repo も候補にする。

-r -a -b は互いに排他。再帰探索は並列に行い（ignore クレートの並列 walker）、.git の中には降りない。

処理

  1. 候補パスのうち git repo（2.6）であり、既に登録済みでないものを新規とする。
  2. 新規 0 件なら No new repos found!。1 件以上なら Found N new repo(s).。
  3. 名前を決める。既定は末尾のディレクトリ名。既存 repo 名と重複するか、今回の新規同士で同じ末尾名が 2 個以上あるときは 親ディレクトリ名/末尾名 にする（区切りは OS によらず /）。
  4. repos.json に追加する。新規はパスでソートした順に並べる。
  5. -a のとき 5.1.1 の方法でグループを作り、Created N new group(s). を出す。
  6. -g のとき、既存グループなら和集合をソートして保存し、なければ新規作成する。Added N repos to the G group を出す。

5.1.1 自動グループ（-a）

引数のパス P（例 /home/u/src）の配下にある repo /home/u/src/project1/repo1 は、P の末尾名と途中のディレクトリを並べた列 (src, project1) を持つ。この列の各接頭辞をグループにする。

src           -> path /home/u/src           メンバー: 配下の全 repo
src-project1  -> path /home/u/src/project1  メンバー: project1 配下の repo

グループ名は接頭辞を - でつなぐ。引数パスの外にある repo はグループを作らない。既存名との衝突の扱いは 14 章。

5.2 scan

gita scan [path]... [-n] [-g GROUP] [--group-path PATH] [-a] [-b] [-s] [-d/--depth N] [-x/--exclude GLOB]...

指定したパスの下を全探索し、見つかった git repo をすべて登録する。path を省略したときはカレントディレクトリを探す。

オプション動作
-n, --dry-run見つかった新規 repo のパスを表示し、書き込まない。
-g, --group / --group-path見つかった repo をグループに入れる。動作は add と同じ。
-a, --auto-groupディレクトリ構造からグループを自動生成する（5.1.1）。-g と併用できない。
-b, --barebare repo も登録する。
-s, --skip-submodulesubmodule を登録しない。
-d, --depth N指定パスから N 階層までしか降りない。既定は無制限。
-x, --exclude GLOB一致するディレクトリには降りない（例 -x node_modules -x "**/target"）。複数指定できる。

探索の規則

  • ignore クレートの並列 walker で探す。.gitignore などの除外設定は使わない（無視されたディレクトリの中の repo も見つける）。
  • 隠しディレクトリにも降りる。.git ディレクトリの中には降りない。
  • repo を見つけてもその中への探索は続け、入れ子の repo も登録する。
  • シンボリックリンク（Windows ではジャンクションも）はたどらない。
  • 読み取り権限のないディレクトリは飛ばし、最後に件数を stderr に出す。
  • 存在しない path は <path> does not exist を stderr に出して飛ばし、他のパスの探索は続ける。終了コードは 1。

処理

  1. 探索中、端末が TTY なら stderr に見つけた件数を 1 行で更新表示する。
  2. 見つかった repo のうち未登録のものを新規とする。Found N new repo(s), M already registered. を出す。
  3. 名前の決定、登録、グループ作成は add の処理 3〜6 と同じ。

5.3 rm / rename / ls / clear

コマンド動作
gita rm <repo>...登録を外す（ディスク上は消さない）。所属グループからも外し、空になったグループは消える。
gita rename <repo> <new>repo 名を変える。new が使用中なら <new> is already in use! を出して終了コード 1。所属グループのメンバー名も置き換え、メンバーをソートし直す。登録順の位置は変えない。
gita ls全 repo 名を空白区切りで 1 行に出す。
gita ls <repo>その repo の絶対パスを出す（cd `gita ls x` 用）。
gita clearrepo とグループとコンテキストをすべて消す。確認は取らない。

5.4 group

コマンド動作
gita group / group ll全グループを表示する。グループ名は下線付き（\x1b[4m）で 名前: path、続けて各メンバーを - repo。
gita group ll <g>そのグループのメンバーを空白区切りで 1 行に出す。
gita group lsグループ名を空白区切りで出す。
gita group add <repo>... -n <g> [-p PATH]グループに追加する。既存なら和集合をソートし、-p 指定時のみ path を更新する。なければ作る。
gita group rmrepo <repo>... -n <g>グループから外す。グループが存在しなければ終了コード 1。
gita group rename <g> <new>改名する。コンテキストがそのグループならコンテキストも新しい名前にする。
gita group rm <g>...グループを消す。コンテキストがそのグループならコンテキストを null にする。

5.5 context

コマンド動作
gita contextコンテキストがあれば g: repo1 repo2。auto で該当なしなら auto: none detected!。なければ Context is not set。
gita context <g>context をグループ名にする。
gita context autocontext を "auto" にする。
gita context nonecontext を null にする。

5.6 flags

コマンド動作
gita flags / flags llflags を持つ repo を repo: --a --b の形で出す。
gita flags set <repo> <flags...>残りの引数すべてを flags として保存する（- 始まりもオプション扱いしない）。0 個なら flags を消す。

flags は委譲系・super・ll・freeze の全 git 呼び出しで git の直後に挿入する。例: gita st dotfiles → git --git-dir=... --work-tree=... status。

5.8 info

コマンド動作
gita info / info llIn use: a,b,c と、未使用があれば Unused: d,e（ソート済み）。

6. ll と状態判定

gita ll [group] [-C/--no-colors] [-g]
  • group 省略時はコンテキストのグループ。どちらもなければ全 repo。
  • -g: グループ指定ありならグループ名の行 g: のあと各行を字下げして出す。指定なしなら全グループを順に同じ形で出す（グループに属さない repo は出ない）。
  • repo は名前でソートして出す。情報収集は全 repo 並列で行い（10.4）、ソート順で先頭から揃った行を順に出力する。全 repo の完了を待たずに表示が始まる。

6.1 1 行の組み立て

{name を (最長の名前の長さ + 1) 桁に左詰め}{各項目を ' ' で連結}

-g のときは行頭に 3 文字の空白を付ける。

項目生成方法書式
branch6.2 と 6.3{color}{info:<18}{end}。info は {branch:<10} [{dirty}{staged}{stashed}{untracked}{situ}]。-C なら色なしで {info:<18}
branch_name6.2そのまま
commit_msg6.4そのまま
commit_time6.4(3 days ago)
path設定値cyan。-C のときは色なし

各項目は layout の幅で切り詰める。幅 w が 0 か未設定なら何もしない。w < 3 なら 3 とする。文字数が w を超えたら先頭 w-3 文字 + ...、超えなければ w 桁まで右を空白で埋める。symbols は角括弧を含む文字列全体に適用する。

6.2 ブランチ名

6.3 の git status 出力の branch.head から取る。(detached) のときだけ git [flags] describe --tags --exact-match を実行し、成功すればタグ名、失敗すれば空文字にする。

6.3 状態判定

repo の状態は gix で読む（11.5）。git コマンドに切り替えた repo では、次の 1 回の git 呼び出しで取る。判定の規則はどちらのバックエンドでも同じ。

git [flags] status --porcelain=v2 --branch --show-stash -z --untracked-files=normal
出力判定
# branch.head <name>ブランチ名。
# branch.upstream が無い、または # branch.ab が無いno_remote（upstream 未設定、または upstream が消えている）。
# branch.ab +A -BA=0, B=0 → in_sync、A>0, B=0 → local_ahead、A=0, B>0 → remote_ahead、両方 >0 → diverged。
# stash Nstashed。
1 XY ... / 2 XY ...X が . 以外 → staged、Y が . 以外 → dirty。
u ...（未マージ）dirty と staged の両方。
? pathuntracked。
  • local と remote の関係はコミット数で判定する。内容が同じでもコミットが違えば in_sync にならない。
  • 出力は最後まで読まなくても、dirty・staged・untracked がすべて真になった時点で読み捨ててよい（ヘッダ行は先頭に出るため）。
  • git が 2.35 未満で失敗したときは、git --version を確かめて要件を示すメッセージを出す。
  • bare repo では status が失敗するため、記号は空、situ は git [flags] rev-list --left-right --count HEAD...@{u} で判定する。
  • stash の判定は git に任せるため、worktree や flags 指定の repo でも正しく出る。

6.4 コミット情報

commit_msg か commit_time を表示するときだけ、次の 1 回で両方を取る。status と同時に並列で起動する。

git [flags] log -1 --format=%s%x1f%cr

%s は件名、%cr は相対時刻（例 3 days ago）。コミットが無い repo では両方とも空文字。

git コマンドで読む場合、ll の git 起動回数は repo あたり 1〜2 回（detached HEAD のときだけ 3 回）になる。

7.2 処理

  1. repo 引数を 4.2 で解決する（引数 0 個かつ allow_all なら全 repo またはコンテキスト）。
  2. repo ごとに argv を作る。先頭が git で flags があれば、git の直後に挿入する。shell 型では flags を挿入しない。
  3. 対象が 1 件、または定義の disable_async が真なら逐次モード（10.1）。それ以外は並列モード（10.2）。シェル型も並列モードで動く。

-s/--shell は値を取らないフラグで、指定すると cmd をシェル経由で実行する。委譲コマンドは repo 指定より後ろの追加引数を受け付けない。追加引数を渡したいときは super を使う。

8. super / shell

コマンド動作
gita super [repo|group]... [--] <git-args...> [-q]4.2 で対象を解決し、残りを git の引数として 7.2 の 2〜3 と同じく実行する。逐次にするかは、残りの先頭語が既定定義のうち disable_async のもの（log show difftool mergetool）に一致するかで決める。
gita shell [repo|group]... [--] <cmd...> [-q]残りを空白で連結した 1 文字列をシェルで実行する。並列モード（10.2）で実行し、stdout と stderr を合わせて取り込み、各行に repo: を付けて出す。
  • 残りが空なら Missing commands を出して終了コード 2（4.3 の案内を付ける場合あり）。
  • -q/--quote-mode: 残りを 1 語（クォートされた文字列）に限定する。例 gita shell -q repo1 "ls | wc -l"。
  • -q 以外の - 始まりの語はすべて残りに含める（clap では trailing_var_arg + allow_hyphen_values）。-q は残りの前にだけ置ける。
  • シェルは Unix で sh -c、Windows で cmd /C。

9. freeze / clone

9.1 freeze

gita freeze [-g GROUP]

グループ指定がなければコンテキストを使う。次の JSON を stdout に出す。

{
  "version": 1,
  "repos": [
    { "name": "gita", "url": "https://github.com/nosarthur/gita.git",
      "path": "/home/u/src/gita", "type": "", "flags": [], "branch": "master" }
  ],
  "groups": {
    "src": { "path": "/home/u/src", "repos": ["gita"] }
  }
}
  • url は git remote get-url origin、失敗すれば git remote の先頭の remote の URL。どちらも無ければその repo は出さない。
  • 同じ url の repo は最初の 1 件だけ出す。
  • branch は 6.2 の方法で取る。repo ごとの取得は並列に行う。

9.2 clone

gita clone <URL|FILE> [-C DIR] [-p] [-n] [-g GROUP | -f]
形動作
gita clone URL [-C DIR] [-g G]DIR（既定はカレント）で git clone URL を実行し、できた DIR/<repo名> を add と同じ処理で登録する。-g があればグループにも入れる。既に登録済みなら URL already in gita.。
gita clone -f FILE [-C DIR] [-p]freeze の JSON を読み、全 repo を並列に clone する。-p 指定時は記録された path に clone する。clone 直後に、branch が空でない repo だけ同じタスク内で checkout する（clone 全体の完了を待たない）。最後に未登録の repo を登録し、グループを group add と同じ処理で反映する。
-n, --dry-run実行せず、repo ごとに git clone URL [path] を表示する。
  • clone 先の repo 名は URL の最後の /（または :）以降から末尾の .git を除いたものとする（git 自身の規則）。

10. 実行モデルと並列度

10.1 逐次モード

  • repo ごとにパスを 1 行出力し、子プロセスを端末に直結（stdin/stdout/stderr 継承）して実行し、終了を待つ。
  • pager やエディタを使うコマンド（log difftool など）はこのモードで動く。

10.2 並列モード

  • 子プロセスを並列数（10.4）まで同時に起動する。stdin は null、stdout/stderr はパイプで取り込む。
  • 環境変数 GIT_TERMINAL_PROMPT=0 を付け、子プロセスを新しいセッション（Unix は setsid、Windows は CREATE_NEW_PROCESS_GROUP）で起動する。認証が必要な repo は入力待ちで止まらず、すぐ失敗する。
  • プロセスが終わった順に、stdout の各行、続けて stderr の各行に repo: を付けて出力する。1 repo の出力は 1 回の書き込みでまとめて出し、他の repo と行が混ざらないようにする。
  • 終了コードが 0 以外の repo は、全体の完了後にパスを出してから逐次モード（flags 付きの同じ argv）で再実行する。認証入力が必要な repo はここで入力できる。

10.3 終了コード

コード場面
0正常終了。
1設定ファイルの破損、グループ名不正、名前の重複など。委譲先が失敗したときの扱いは 14 章。
2引数エラー、Missing commands、quote mode や -- の違反。

10.4 並列度

処理既定の並列数
ll、freeze の情報収集gix で読む repo（11.5）は CPU 数。git コマンドに切り替えた repo は min(repo 数, CPU 数 × 4) で、repo 内の status と log も同時に起動する
委譲コマンド、super、shell、clone -frepo 数（全部同時）
scan、add -r/-a の探索CPU 数
  • git コマンドの並列数に上限を設けるのは、git status がディスク読み取りと CPU を両方使い、repo 数ぶん同時に起動すると Windows でプロセス生成とディスクの取り合いが起きて逆に遅くなるため。倍率は 12 章のベンチマークで決め直す。
  • 委譲コマンドは主にネットワーク待ちなので上限を設けない。
  • 並列数は -j/--jobs N、環境変数 GITA_JOBS、settings.json の jobs の順で上書きできる。-j 1 で全処理が直列になる。
  • プロセスの起動と待機は標準ライブラリのスレッドで行う。並列数ぶんのワーカースレッドが共有のキューから repo を取る。

10.5 Windows

  • 起動時に仮想端末処理（ANSI エスケープ）を有効にする。
  • stdout がパイプでも -C 以外では色を付ける。
  • git は PATH から一度だけ解決し、以降は絶対パスで起動する（Windows の PATH 探索を毎回行わない）。

11.4 設定の書き込み

  • 同じディレクトリの一時ファイルに書いてから rename で置き換える。途中で中断しても設定が半端に残らない。
  • 読み込みから書き込みまでの間、設定ディレクトリの .lock に排他ロックを取る。2 つの gita が同時に add しても片方の変更が消えない。
  • 書き込み前に設定ディレクトリを作る。

11.5 状態の読み取り（gix と git コマンドの切り替え）

ll と freeze が読む情報は、まず gix（gitoxide。Rust だけで書かれた git の実装）でプロセス内から読み、うまくいかない repo だけ git コマンド（6.3、6.4）に切り替える。委譲コマンド、super、shell、clone は常に git コマンドで実行する。

gix で読む情報

情報git コマンドでの対応
ブランチ名、detached 時のタグ名branch.head、describe --tags --exact-match
dirty、staged、untrackedstatus の各エントリ
stash の有無refs/stash の存在
upstream との ahead/behindbranch.ab
最新コミットの件名と相対時刻log -1 --format=%s%x1f%cr
remote の URL（freeze）remote get-url origin

git コマンドに切り替える条件

repo ごとに判定し、次のどれかに当たればその repo だけ git コマンドで読み直す。

  1. repo に flags が設定されている（任意の git オプションの意味を gix で再現できないため）。
  2. gix で repo を開けない、または読み取りの途中でエラーになった。
  3. repo が gix の未対応機能を使っている。対象の一覧（index の拡張、extensions.* の設定、sparse checkout など）は実装時に gix の対応状況を調べてコードに持つ。
  • 切り替えは黙って行う。GITA_DEBUG=1 のときだけ、repo 名と理由を stderr に出す。
  • 一部の情報だけ git コマンドで補うことはしない。1 つの repo の情報は必ずどちらか一方のバックエンドで揃える（判定の食い違いを避ける）。
  • settings.json の backend（"auto" "gix" "git"、既定 "auto"）と環境変数 GITA_BACKEND で固定できる。"gix" 固定のときは切り替えず、読めない repo はエラー表示にする。
gix の status 機能の対応範囲と API は、バージョンによって変わる。実装開始時に最新の gix で上の 6 項目が読めることを確かめ、読めない項目があればその項目を表示するときは常に git コマンドを使う。

13. 実装順序

  1. 設定ディレクトリの解決、repos.json settings.json の読み書き、ロックと単体テスト。
  2. add（-r/-a/-b/-s/-g/-n）、scan、rm、rename、ls、clear。
  3. group、context、flags。
  4. 状態判定（git コマンド版）と ll、color、info。ここで速度計測を作る。
  5. gix バックエンドと切り替え処理、バックエンド比較テスト。
  6. 実行エンジン（逐次・並列）と委譲コマンド、super、shell、-- 区切り。
  7. freeze、clone。
  8. 補完スクリプト、Windows 対応の確認、リリース（cargo install、GitHub Releases のバイナリ）。

14. 決定事項

  1. 逐次実行または再実行後に 1 件でも失敗していれば、終了コード 1 を返す。
  2. repo 名や各項目の表示幅を unicode-width で測り、端末上の桁数で揃える。
  3. 自動グループ名が既存のグループ名と重なり、パスも一致するときはメンバーを追加する。パスが異なる場合や repo 名と重なる場合は、警告を出してそのグループへの追加を飛ばす。
  4. add -r/-a と scan のどちらでも再帰探索できる。
  5. scan で見つからなかった repo は登録に残す。登録を外すには rm を使う。
